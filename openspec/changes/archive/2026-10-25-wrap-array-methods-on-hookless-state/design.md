# Design

## Context

See proposal.md, Why. Verified on a fresh build of trunk `cbd7448` on 2026-10-21; the reproductions and decisions are in the triage notes of `.do/inbox/2026-10-21-hookless-state-skips-array-method-wrap.md`. What shapes the approach:

- The two get handlers that `state()` installs differ in one step: the hooked one asks for a wrapped method before returning a non-object value, the hookless one does not. The wrapper lookup already checks for an array target, a string property in the mutating-method set and a function value, so it is cheap to call on the hookless path.
- The current wrapper applies the native method to the raw target and then schedules every subscriber of the array without a property. Nothing passes a trap, so the loop check, dependency tracking and state hooks do not run. The self-wake it issues inside an effect is dropped by the effect's active guard.
- A native mutating method run on the Proxy reads `length` (and the indices it moves) through the get trap and writes them through the set trap. Inside a synchronous top-level effect that trips the loop check on `length` or an index. Outside an effect each write schedules per property and flushes separately unless a batch is open. A write of an equal value does not notify.
- Inside a batch, writes from outside an effect on hookless state take the fast path that records dirty targets; at the outermost boundary a dirty array schedules every subscriber of the array once. That is the one-wake-per-call behavior that triage decided on (Q24 a), already implemented for batched hookless writes. State created with an `onWrite` hook gets a different set trap that never takes the fast path and schedules per property even inside a batch, and the fast path calls no hook (Q34, verified on `e9bc6cd`: an effect reading only index 1 re-ran 0 times after a batched write of index 3 with `onWrite`, 1 time without; `onRead` alone changes nothing).
- The wrapper is called as a method, so its `this` is the Proxy the caller went through. Sealed and frozen targets have no proxy back-reference property, so a lookup from the raw target would need the fallback cache; the receiver needs no lookup.

## Goals / Non-Goals

**Goals:**
- One set trap for every state object, so the presence of a hook never changes which subscribers wake or when, and `onWrite` observes every changing write including batched ones.
- One code path for every read and write an array method performs, on both kinds of state.
- At most one wake per call, from the existing batch boundary.
- No new state, counter or exemption in loop detection.
- The hookless read path stays within 1% of trunk on the benchmark.

**Non-Goals:**
- Per-property wakes for array methods.
- Changing the numeric caps in loop detection, or any other loop-detection logic.
- Changing how plain index or `length` assignments notify.

## Decisions

- **One set trap for all state; `onWrite` is an observer on every path (Q34 a, Q36 a).** The trap keeps the hookless notification logic, batch fast path included, and calls `onWrite` after the raw write wherever a value changes, including inside the fast path. Hooks return `void` and fire after the operation (hooks roadmap, contract facts 1 and 3), so they cannot steer notification; a trap chosen by hook presence contradicted that. Alternative: keep two traps and relax the spec to per-property wakes on hooked state; rejected because it keeps hooked and hookless behavior apart, which the change exists to end. This lands in its own ticket before the wrapper, because it also changes plain batched writes on hooked state.
- **The wrapper applies the native method to its call receiver (`this`) inside a batch, and returns the result.** The receiver is the Proxy, so every read and write passes the traps. Alternative: look the Proxy up from the raw target through the back-reference symbol or the proxy cache; rejected because the receiver is already the right object and the lookup has a fallback branch for non-extensible targets that the receiver avoids.
- **The batch is the hookless `batch()` or its inlined depth bookkeeping; the implementer picks by the benchmark.** The public `batch()` without hooks is exactly the depth increment, dirty-target flush and effect flush the wrapper needs. Inlining avoids one closure per call. Alternative: a new internal "suspend notifications" flag; rejected because the batch mechanism already exists and composes with user batches.
- **Both get handlers call the same wrapper lookup, placed before the non-object early return.** The lookup's first check is `Array.isArray` on the target, so a plain object read pays one call and one check. Alternative: keep the hookless handler untouched and special-case arrays at `state()` creation; rejected because nested arrays are wrapped lazily on read, so the get handler is where the decision has to live.
- **A call that changes nothing wakes nobody.** This follows from routing writes through the set trap, which skips equal values, and matches the rule for direct assignments. Alternative: force a wake per call, as the current hooked wrapper does; rejected because it would need an extra scheduling call that the batch boundary does not provide and would notify without a state change.
- **The method cache keys stay as they are unless the implementer finds a simpler shape.** The wrapper no longer closes over the target, so a cache keyed by native method alone would serve, but identity per target is what the existing tests may rely on; the implementer checks before changing it.
- **Dependencies the method reads are tracked like any read.** An effect that calls a mutating method now depends on `length` and the indices the method touched. For synchronous top-level effects that is moot, since the call throws. For child and microtask effects it matches what hookless state does today.
- **Docs change in the same tickets as the behavior they describe.** The two agent docs name array interception and say what the code does once ticket 05 lands. The two handbook pages wait for the release tree that carries the behavior (Q35 c), recorded in the inbox.
- **Benchmark case: one subscriber on an array, a loop of `push` then `pop`, measured on both kinds of state, added before any library change.** It is the pattern the proposal changes. The baseline is the full suite run on the unchanged library with the new case present; the gate is the grand total of a full run on the final commit, at most 1% above the baseline (Q27 b, Q33). Below the gate the change is not complete: ticket 06 iterates on the set trap, the wrapper and the lookup until a full run meets it.
- **`push` and `pop` run the native method on the raw target and do the trap bookkeeping themselves; the other five methods keep the Proxy receiver (Q52 a).** Ticket 06 measured about 47% of the array-case self time inside V8's generic push and pop on a Proxy receiver, and trunk's raw-target wrapper shows the native work plus one wake costs about a third of that. For `push` and `pop` the properties read and written are fixed (`length`, the last index), so the direct path can reproduce what the traps would have seen, with a plain Proxy over the same array as the reference: `onRead` for the method name and the properties read, `onWrite` with the loop check for each property the set trap would have written, `onDelete` for the index `pop` removes (the delete trap has no loop check and no equal check, Q57 a), an equal value staying silent, one wake per call outside an effect, and per-property scheduling inside a child or microtask effect as the set trap's effect path does (Q58 a). A new test file pins that sequence and the wake set for both methods on both kinds of state (Q59 a). The five methods whose read and write pattern depends on the arguments stay on the Proxy receiver, because reproducing their trap sequence by hand is where correctness would be guessed.
- **A write of `undefined` to an absent property is a change, not an equal value (Q65 a).** The set trap's equal check compared the new value with `rawTarget[prop]`, which is `undefined` for an absent index, so `push(undefined)` and `list[n] = undefined` on trunk's hookless path stored nothing and woke nobody, and tickets 02 to 06 spread that to hooked state. The check now applies only to a property that exists; the direct path of ticket 07 does the same. Principle 1: a hookless mutation changes the state and notifies.

## Risks / Trade-offs

- [Each element move inside `shift`, `unshift`, `splice`, `sort` and `reverse` becomes a trap call, which hooked state did not pay before] → it is what hookless state pays today for the same call, and the benchmark grand total measures it; if the final run exceeds the baseline by more than 1% the change waits for the performance ticket to bring it back.
- [A consumer relied on hooked state waking subscribers on a `sort` or `reverse` that changed nothing] → undocumented; the handbook describes wakes as reactions to changes. To be called out in the notes of the release that carries the behavior.
- [The hookless read path pays an extra function call per property read] → the lookup returns on its first check for non-arrays; the `state read no effect` benchmark case gates it at 1%.
- [A consumer called a mutating method inside a synchronous top-level effect on hooked state and depended on the silent stall] → the stall was a dropped notification, and the effect never observed its own write; the loop error now names the effect and the property, which is the documented behavior.
- [The direct `push` and `pop` path calls a hook or wakes a subscriber the Proxy path would not have, or misses one] → the spec scenarios of tickets 03 and 04 pin both kinds of state and stay untouched; ticket 07 adds no exemption and changes no test; a divergence fails the suite before the benchmark is read.

## Migration Plan

No version bump in this change (Q35 c): the user expects further inbox items to make the next release a breaking one, so the behavior ships with that release and the handbook pages are written for its tree then. The trunk publish workflow is gated by a version change, so merging publishes nothing. Order inside the change: the set trap, then the wrapper and the notification tests, then the loop-detection and hook assertions, then the benchmark comparison and agent docs, then the performance gate, so every commit on the branch is green. Rollback: revert the squash commit; no data or API shape changes.
