# Library-wide performance tournament

**Status:** ready-for-agent

The maintainer asked (Q53, 2026-10-23) whether the whole library can be faster, and set the method: a tournament over the four ways software gets faster, applied one at a time to a measured baseline. The four moves: (1) do less work per operation, fewer instructions, allocations and indirections on the hot path; (2) do the work less often, cache a result, batch repeated work, skip work whose input did not change; (3) change the algorithm or data structure so cost grows slower with input size; (4) move work off the hot path, precompute, defer, or stop doing it where nobody observes it. Protocol: measure the baseline; apply one candidate per move on the baseline and measure each alone; keep the moves that are faster than the baseline; apply every pair of survivors on the baseline and measure; keep the pairs that beat the baseline; combine the surviving pairs and measure; the survivor is the true optimization. The same tournament can compare different approaches to one move. The rule throughout: Beacon must be faster over time, never slower, and 1% is treated as noise.

What the record says about noise, which the protocol has to absorb before any arm is judged: the same code measured 20127.94ms on 22 October (ticket 05 report line 24) and 20548.19ms on 23 October (ticket 06 report, attempt 0), a 2.1% drift between days; within one run, `state no subs` printed sd=6.99ms on a 40.35ms median, `state + derive` sd=15.27ms on 173.73ms, `batch + derive` sd=5.70ms on 44.16ms (ticket 06 report, attempt 0 output), so several cases vary by 10% or more inside three cycles. A single three-cycle run cannot resolve a 1% difference on those cases. The tournament therefore needs: an A/A test first (the baseline run twice, interleaved, to learn the real noise per case); every arm measured interleaved with the baseline in one session, at least three runs each, medians compared per case; and a verdict per case of faster, slower or indistinguishable, where indistinguishable means within the A/A spread of that case. A candidate counts as a win only on cases where it is faster beyond that spread and slower on none. Where the suite's cases are too noisy to resolve, the benchmark script needs more cycles or isolated targeted cases before the tournament can judge, which is itself a first ticket.

Proposed as a new OpenSpec change after `wrap-array-methods-on-hookless-state` archives; ticket 07 of that change uses the interleaved measurement already.
